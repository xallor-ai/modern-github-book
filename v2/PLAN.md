# 《现代 GitHub》全书大纲与章节写作设计

更新：2026-11-20。状态：供讨论的第二版大纲，尚未确认全书正文定稿。

本文是编辑计划，不是读者正文。基于 PR #4 的重写提案补充：保留机制讲解和可重复实验，恢复已经确认的零基础读者定位，补足从文档协作到程序开发的桥梁，调整知识依赖。现有第 4 章样章保留待评，不以字数增长或脚本通过认定出版质量。

## 一、读者与最终目标

主读者有基本电脑操作能力，Git/GitHub 零基础，希望参与开发并使用 AI 自动化。不能假定其已会 clone、commit、push、PR、Python 或 YAML。前七章不要求编程，第八章补足后续 CI 所需的小程序知识。已有经验的读者可以依据前置知识跳读。

核心路线带读者完成：修改文件、形成提交、同步远端、提出和评审 PR、自动测试、配置合并门禁、发布静态站点和恢复错误发布。进阶部分教长期维护、自托管执行、AI 委派及 API/App 扩展。

普通命令使用 Windows Git Bash；Runner 服务管理等系统操作在相关位置说明终端差异。正文先教会读者，再要求其核对结果。代码正确和可复现是底线；能解释原因、预测变化和迁移应用才是教学完成。

## 二、五部分、20 章与阅读路线

建议五部分、20 章，另设前言、综合实践和参考附录。章数来自主题和前置关系，不是出版页数配额。

| 部分 | 章节 | 核心问题 | 学习结果 |
| --- | --- | --- | --- |
| 一、认识 GitHub，掌握 Git | 1–4 | 修改在哪里，如何保存、协作和恢复？ | 能用网页和本地工具修改文件，理解提交与分支，处理冲突和错误 |
| 二、把个人修改变成团队工作 | 5–8 | 需求如何变成可评审、可测试的成果？ | 能组织 Issue/PR、接收贡献，读懂和改进小程序 |
| 三、让检查自动执行 | 9–12 | 谁执行配置，何时执行，失败如何影响合并？ | 能从零写 CI，理解产物和执行环境，按需使用自托管 Runner |
| 四、发布、部署与长期维护 | 13–16 | 如何交付版本并持续保持可用和可信？ | 能发布、审批、回滚，管理权限、依赖、成本和故障 |
| 五、AI 协作与平台扩展 | 17–20 | 哪些工作可以委派，怎样连接外部程序？ | 能验收 Agent，理解事件自动化、API、App 与 Webhook |

核心顺序是 1–11 → 13–14。第 12 章自托管 Runner、第 18 章云端模型、第 20 章 App/公网服务有额外环境要求，可以按需学习；它们不阻塞基础路线。第 15–16 章面向长期维护，第 17–20 章面向 AI 与集成。选读章仍须完整讲清自己的任务，不能降为术语清单。

## 三、贯穿项目的演进

resource-nav 始终围绕维护学习资源、校验清单、生成和发布导航页面。复杂度由需求引出，不为了展示功能将它扩成大型应用。

| 阶段 | 项目变化 | 教学理由 |
| --- | --- | --- |
| 1–4 | README 与少量文本资源；独立沙盒演示冲突和恢复 | 学 Git 不依赖编程；不把练习事故带进主项目 |
| 5–7 | 收录需求、子 Issue、PR、贡献指南和模板 | 先理解人工协作，再将规则交给程序 |
| 8 | CSV、校验器、测试与 HTML 生成器 | 从人工检查遗漏引出程序和测试 |
| 9–10 | Hello workflow、自动测试和门禁 | 将已有本地命令迁移到远端执行环境 |
| 11 | artifact、小范围环境矩阵、并发取消 | 从保存结果、兼容性和重复运行引出机制 |
| 12 | 独立私有 runner-lab | 支撑特殊环境、重型 CI 和额度不足等需求 |
| 13–14 | Release、Pages、Environment、回滚 | 对外交付有版本、可追溯的成果 |
| 15–16 | 权限维护、更新与可选链接健康报告 | 区分确定性测试和外部网络的偶发失败 |
| 17–18 | Agent 补测试、分析资源变化、受控评论 | 沿用已经建立的 PR、CI 和人工验收 |
| 19–20 | API 查询、App 身份和事件接收 | 解释跨系统访问，不与普通 workflow 混写 |

不将 3×3 矩阵、PyPI、数据库、复杂前端或 Kubernetes 设为必修。矩阵从两个有价值的环境开始；有实际依赖或耗时步骤时才演示缓存。外部链接检查不应因第三方偶发超时阻断全部 PR。

重要阶段提供可下载的配套文件和版本快照；只有真实创建后才能列出 tag。快照帮助中途加入与恢复，不要求读者每节重建分支。分支和工作区状态仅在教学或操作依赖它时说明，不在每章重复内部状态契约。

## 四、逐章内容设计

每章先定义读者学完能做出的解释、操作与判断，再据此安排章节内容。下列学习成果是写作与审稿约束，不是宣传语，也不是作者已经完成教学验证的声明。编号用于追踪内容覆盖，不表示所有成果难度相同。

- 每项成果必须有对应的机制解释、示例或练习支持；仅出现术语、列出步骤或给出成功截图，不能判为达成。
- “理解、掌握、熟悉”不能单独作为成果；需写成可观察行为，例如“解释为什么缺少 checkout 会找不到项目文件”。
- 写完一章，作者逐项填写支持该成果的实际段落与练习位置；审稿分别判断解释是否充分、操作能否完成、读者能否独立作出判断。
- 发现承诺无法支持时，补充教学内容、调整前置或将该成果明确移至选读，不能只在措辞上降低问题的严重性。
- 后章可以依赖前章已承诺并教会的成果；未教的能力不得成为隐含前提。依赖其他账号或公网环境的操作成果，应分别标明概念学习、局部练习和真实操作完成状态。
- 这些约束保存在大纲和审稿记录中。正文用自然讲解呈现，不把成果编号、覆盖表和评审记录搬给读者。

各节可交替组织解释和实验。当前每章先列三个核心成果，具体写作发现需要进一步拆分时可以调整，不将三个视为固定配额。

- 1.6 在文件和历史页面找到结果，认识公开与私有范围。

示例：一条资源说明的修改前后，连接文件、提交与讨论。学会标准：能指出每种对象保存什么，并找到某次修改及原因。完整 PR 评审留到第 6 章；不做菜单逐项导览。

- 4.7 推送了凭据：先撤销，为什么只 revert 不够。

## 五、如何保证每章讲清楚

### 1. 统一教学要求，不统一十二个标题

每个主要知识点应回答：解决什么问题；输入输出是什么；中间发生什么；怎样操作；为什么出现该结果；改一个条件会怎样。解释与实践可以交替。已经讲过的内容适当回指，不反复展开。

例如不能只写“uses 使用 action”。要用 checkout 解释调用对象、获得的文件、后续 run 的工作位置，以及缺少 checkout 为什么找不到代码。恢复章适合状态图，App 章适合时序图，PR 章适合差异与评论例子，不规定每章同样多的图和故障。

### 2. 写作前检查知识依赖

| 知识依赖 | 安排 |
| --- | --- |
| PR base/head 需要分支知识 | 3 → 6 |
| CI 需要会运行测试及识别失败 | 8 → 10 |
| YAML 和 runner 先于完整 CI | 9 → 10 |
| required check 需要已有检查 | 10 先运行 CI，再配 Ruleset |
| 跨 job 文件需要理解执行隔离 | 9–10 → 11 |
| 部署审批需要知道部署改变什么 | 14 先解释部署，再配置 Environment |
| AI 验收需要评审与测试方法 | 6、8、10 → 17 |
| App/Webhook 需要请求与身份知识 | 15、19 → 20 |

每章列出首次出现的术语，标记本章解释或前文位置。依赖不存在，就补解释、调整顺序或分为选读，不能交给读者自行补课。

### 3. 四种学习证据与三类审查

| 学习证据 | 怎么检查 | 不合格表现 |
| --- | --- | --- |
| 能解释 | 用自己的话说明原因 | 只能复述术语 |
| 能预测 | 改一个参数，先判断结果 | 配置稍变就只能重新复制 |
| 能完成 | 仅按正文从起点做到结果 | 依赖作者机器或隐藏设置 |
| 能迁移 | 换一个需求或小项目 | 只会书上唯一案例 |

练习提供提示、可判断的结果和独立参考解答。技术审查查事实与可运行性；读者审查记录第一次不理解的位置；编辑审查查论述深度、必要性、顺序和重复。三者分别给结论，不能用“没有 P0/P1”替代出版质量评价。

### 4. 验证服务于讲解

正文保留原理、例子、必要前提、预期现象和诊断依据。实验脚本与示例有下载入口。作者记录保留版本、命令、run 链接、错误原文及未验证范围，不逐项搬进正文。

脚本通过不等于读者能照书做，需另走一遍只读正文的路径。脚本准备不能隐藏正文缺失的步骤；不得直接删除未核验的可配置目录，应使用新建独立临时目录。安全与权限问题首次出现就说明，不能先教危险用法再等后章纠正。

### 5. 篇幅与资料的处理

不设每章统一字数，也不把短视为简洁、长视为深入。基础章、复杂机制章按需要分配篇幅；统计正文和代码分开，成稿后用排版样张估算出版体量。短章查跳步，长章查重复和是否混入多个独立主题。

学习官方与成熟社区资料的解释方法，引用必要的短例、图示或代码时核对适用版本及许可。主例需要的知识留在书中，外链用于出处和深入阅读。复杂参考不必穷举，更不能复制全文凑字数。

### 6. 提纲阶段固定的编辑约束

| 项目 | 约束 | 写作与审稿如何执行 |
| --- | --- | --- |
| 能力终点 | 核心路线独立维护并交付小项目；进阶路线学会选择与实施特定扩展 | 不以覆盖所有 GitHub 功能或“精通所有工具”为承诺 |
| 入章前提 | 每章标明已有能力，新术语首次出现有解释 | 引用前章学习成果；依赖未被教授时先补桥梁，不能让读者外出补课 |
| 深度分级 | 独立使用、解释并选择、知道用途三档 | 以上各章已标注；核心任务至少达到独立使用，选读内容不冒充必修能力 |
| 主题归属 | 一个知识点在一个位置首次完整讲解 | 后章回指并补新情境；更改归属时同步前置与练习，不重复整段教学 |
| 项目演进 | 新复杂度来自具体需求 | 不为展示工具强加包工程、矩阵、缓存或基础设施 |
| 环境门槛 | 核心路线不强制付费产品、第二账号、GPU 或公网接收服务 | 明确 GitHub 账号、联网等基本条件；主例使用满足所需功能的环境，套餐变化单独核对 |
| 示例递进 | 先可理解的最小例子，再增加一个变量，最后给可运行整合例子 | 不能直接贴最终配置后要求读者核验；整合文件必须与正文演进一致 |
| 练习与解答 | 有解释、预测、操作或迁移任务，给必要提示与参考思路 | 解答另置但入口明确；答案不只是运行截图或一份最终代码 |
| 表达 | 真实需求引出机制，假设案例明示 | 不编造事故；不反复写内部工作区契约；复杂语法可简述，主例所需知识不能省略 |
| 来源与授权 | 一手资料优先，引用/改编与原创区分 | 核对许可及版本，图源可追踪；出处链接不能代替书内解释 |
| 复现 | 版本、配套文件、章节快照与正文对应 | 版本号以核对和实测为准；阶段 tag 仅创建后发布，不给读者不存在的路径 |
| 交付 | 技术正确、普通读者学得会、编辑质量分别审查 | 三项未全部通过不能标为出版定稿；缺少真实运行证据如实保留状态 |

每章写作前应形成：前置能力 → 学习成果 → 知识点及深度 → 讲解顺序 → 核心例子与必要图示 → 练习及解答要求 → 内容边界 → 验收方式。章节设计卡是写作工具，不是正文模板。篇幅、图数量和失败案例数量不设统一配额，先完成连续样章再校准出版规模。

### 7. 截图的获取、制作与验收规范

#### 优先级和缺图处理

- **必需**：核心讲解依赖该界面或可见结果。成稿前应采集并审查；如界面变化，更新方案，不能无声删掉。
- **条件必需**：章内承诺完成的产品/云端实验依赖账号、权限或公网条件。正文保留该实操承诺时必须有真实演示材料；暂不可用就将该实验保持未完成，不用示意图伪装实测。
- **按需**：存在定位困难或界面差异时制作；没有新增教学价值可以省略，并在编辑记录解释理由。
- 本提纲的图号仅用于计划追踪，不代表图片已存在；本轮只编制计划，不新增空图片目录，不把“待截图”占位发布到读者正文。

#### 获取入口与来源

默认截图来自作者控制的 resource-nav 或专用实验仓库。对应章节实际走通后，从表中指定的页面采集；采用哪个账号、仓库、角色、分支和配置须在工作记录中保留，不要求全部出现在正文。

第 12 章采用私有 runner-lab；第 17–18 章采用所选产品的真实任务；第 20 章采用实际注册的实验 App 与受控接收服务。现有额度通知图先检查脱敏、清晰度和历史时间说明，再复用一份源文件。第三方截图须记录原始 URL、日期、许可/授权与改动情况，不从搜索缩略图直接拼成教程。

对比图尽量来自同一实验对象、同一界面缩放和相同裁剪范围。记录运行或对象标识，防止将不同 PR、不同提交、不同账号条件的状态拼接成一次完整过程。画流程和状态模型时使用原创示意图，并明确标为示意，不伪造平台 UI。

#### 每张图的工作记录

使用图号关联：对应小节与学习成果、待采集/已采集/已脱敏/已校对状态、原始来源、采集日期、产品或工具版本、必要账号条件、原始与发布文件路径、标注内容、图注和替代文本。一个截图至少服务一个已列出的学习成果；无法说明服务哪项，就删掉或降为候选。

实际文件采用稳定且有意义的名称，按现有资源目录约定保存；截屏源图和发布图仅在确有编辑需要时分别保留，敏感原图不得进入 Git。正文引用单一发布资源，不在不同章节复制同一图片；后章使用同一界面时优先回指。

#### 画面与隐私

裁剪到理解操作所需区域，同时保留辨认位置的上下文。标注控制在少量关键点，统一编号与图注，不用大红框覆盖全部界面。说明必须有文字对应，不能只靠红绿颜色表达成功或失败。

使用实验数据；排除 token、私钥、密码、设备码、二维码、Cookie、无关用户资料、支付信息与私有路径。使用不可恢复的实色遮盖并导出扁平图，检查元信息；敏感区域能不拍就不拍。不要遮掉解释所必需的分支、实验编号和状态，可事先使用适合公开的实验命名。

GitHub 阅读端按实际显示宽度检查文字是否可读；出版样张同时检查缩印和灰度。必须能在不放大的情况下读到教学关键文字。代码、命令、错误原文、JSON 与表格优先提供可复制文本；截图只补充空间定位和可见结果，不替代正文或代码。

#### 图文关系与验收

图前交代读者要观察什么；图后解释标注所说明的行为、结果及必要限制。图注写具体结论，不只写“截图如下”。每张图配替代文本，关键知识不能仅藏在图内。

审稿逐图核对：画面与文字相符、入口实际存在、对比对象一致、解释因果充分、脱敏完整、来源可追溯、显示清晰。截图只能证明画面所见；例如绿勾不能证明需求正确，单条评论截图不能独自证明幂等，页面能打开不能证明回滚路径已经验证。

### 8. 综合实践与附录的视觉边界

综合实践优先回指前文截图，只补充新的成品页面与必要的新交互，避免再次展示全套操作页面。三个附录以可搜索的文本、表格和链接为主，不强制截图。某个版本出现明显不同入口时，才增加带适用条件的局部图。
