# 《现代 GitHub》第二版：重写计划

## 为什么重写

第一版共约 7.8 万字符，去掉代码后正文约 5.6 万，平均每章不到 3000 字。问题不在字数本身，而在三个结构性原因：

1. 每章只给步骤，不讲机制。读者能照着敲，但一旦现场和书上不同就无从判断；第一版第 03 章的恢复流程本身就因此出错。
2. 每章塞进四五个主题，每个主题只剩一两段。
3. 贯穿项目是 2 行 CSV 加 40 行 Python，撑不起 CI 矩阵、发布、权限治理和 Agent 这些主题。

第一版值得保留的是：学习路径的顺序、lab 仓库加测试报告的验证方式，以及附录 A“真实问题 → 排查 → 解决”的写法。

## 定位

- **读者**：会 `clone`、`commit`、`push`、开 PR 的开发者，以及要为小团队定规则的技术负责人。不从安装 Git 讲起。
- **读完能做什么**：独立把一个开源项目从“能跑”带到“可协作、可发布、可审计、可交给 Agent 分担”，并且在出问题时知道去哪里看、怎么恢复。
- **不写什么**：GitHub 网页按钮的逐一导览；不加验证地罗列功能清单；与 GitHub 无关的通用 Python 教学。

## 贯穿项目：resource-nav

从第一版的资源清单出发，逐章演进成一个真实可用的小型开源项目，配套仓库按章打 tag（`ch05-end` 等），读者可以从任一章的起点开始。

| 阶段 | 章节 | 项目状态 |
| --- | --- | --- |
| v0 | 1–4 | `resources.csv`、`catalog.py`、`build.py`、unittest。沿用第一版资产 |
| v0.x | 5–8 | 改成 `src/resnav` 包，`pyproject.toml`，CLI：`resnav validate / build / check`；链接健康检查功能经 Issue → PR → 评审落地；接受第一个 fork PR |
| v0.x | 9–12 | CI 矩阵（3 个操作系统 × 3 个 Python 版本）、缓存、产物；每日定时巡检失效链接并开 Issue；workflow 安全加固；托管 runner 费用与 self-hosted runner |
| v0.1–v0.9 | 13–15 | 语义化版本、tag、Release、变更日志；PyPI 可信发布与产物证明；Pages 站点加审批与回滚；Dependabot、CodeQL、secret scanning |
| v1.0 | 16–18、终章 | Coding agent 修复失效链接；Agentic Workflow 做每日分诊；GitHub App 机器人；完整发布 v1.0 |

## 每章统一结构

1. **场景**：一个真实会遇到的问题，最好来自实际项目或第一版实验中的真实失败。
2. **机制**：把问题背后的模型讲清楚，配图或配实测输出，不靠形容词。
3. **动手**：在 resource-nav 上完成本章里程碑。
4. **出错时**：至少三个常见失败模式，给出真实报错和排查路径。
5. **团队决策**：给出取舍，而不是唯一答案；说明在什么条件下选哪种。
6. **小结与练习**：练习有可检验的结果。

目标篇幅：每章 1.2–1.8 万字，全书约 23–26 万字。

## 验证机制

- 每章在 `v2/labs/chNN/` 下配一个可重复运行的脚本，正文引用的命令输出全部来自脚本的真实运行，脚本带断言，行为变化时会失败。
- 只能在网页或云端验证的内容（Rulesets、Environment 审批、Copilot、Pages），在配套仓库中留下 run 链接或 API 回执；未验证的写明“未验证”，不写成已通过。
- 正文出现的版本号（Git、gh、Actions、gh-aw）在每章末尾列出“本章验证环境”。

## 目录

### 第一部分 协作的底层模型

**第 1 章 一个 GitHub 项目由什么组成**
仓库、fork、组织、可见性与角色权限；GitHub 对象（Issue、PR、Discussion、Release）之间的关系；resource-nav 的目标架构与全书路线。
里程碑：建立配套仓库，导入 v0 代码。

**第 2 章 Git 的数据模型：对象、引用与三个区域**
blob、tree、commit 的内容寻址；分支和 HEAD 只是指针；工作区、暂存区、提交之间的数据流；远程跟踪分支、ahead/behind。全书后续所有“恢复”“合并策略”的地基。
里程碑：用 `git cat-file` 拆开 resource-nav 的一次提交。

**第 3 章 分支与历史整形：merge、squash、rebase**
三种合并方式在提交图上的差异；冲突的本质与解决流程；线性历史的代价；`rebase -i` 整理提交；团队该选哪种合并策略。
里程碑：为 resource-nav 定下合并策略并写进 CONTRIBUTING。

**第 4 章 出错之后：先判断现场，再选择恢复方式**（样章，已完成）
Git 何时真的删除数据；restore、stash、reset、reflog、revert 的适用边界；revert 合并后再合并的陷阱；force push 覆盖与 `--force-with-lease --force-if-includes`；推送了密钥怎么办；GitHub 侧的安全网。

### 第二部分 从需求到合并

**第 5 章 用 Issue 和 Projects 管理工作**
需求拆分、子任务与依赖关系；Issue 类型与表单；Projects 字段、视图与内置自动化；用 `gh` 批量操作。
里程碑：把“链接健康检查”拆成可执行的子任务。

**第 6 章 写一个值得评审的 PR，做一次有价值的评审**
PR 的大小与拆分；描述该写什么；评审时看什么、怎么提建议；CODEOWNERS；草稿 PR、建议修改、多轮修订。
里程碑：链接健康检查功能经两轮评审合入。

**第 7 章 保护主分支：Rulesets、必需检查与合并队列**
Rulesets 与旧版分支保护的区别；必需检查的命名陷阱；绕过名单；合并队列解决什么问题、什么时候不需要。
里程碑：main 受 Ruleset 保护，禁止 force push 与删除。

**第 8 章 开源协作：fork、外部贡献者与维护者负担**
fork PR 的权限模型；首次贡献者的 workflow 审批；模板、许可证、行为准则、安全策略；如何拒绝一个 PR；维护者的时间预算。
里程碑：接受第一个来自 fork 的贡献。

### 第三部分 自动化

**第 9 章 Actions 的执行模型**
事件、workflow、job、step、runner 的关系；上下文与表达式；`GITHUB_TOKEN` 的权限与生命周期；并发控制；为什么 workflow 没有触发。
里程碑：第一个 CI workflow，并能解释每一行。

**第 10 章 一个可信的 CI**
矩阵、缓存、产物；失败诊断与重跑；不稳定测试的识别和隔离；CI 时长和费用的权衡。
里程碑：3×3 矩阵 CI，失败时上传诊断产物。

**第 11 章 Workflow 安全**
最小权限；`pull_request` 与 `pull_request_target` 的危险差异；第三方 action 固定到 SHA；脚本注入；OIDC 取代长期密钥。
里程碑：对 resource-nav 的 workflow 做一次安全审计。

**第 12 章 Runner 与费用**
托管 runner 的计费与额度；额度耗尽时的现象；self-hosted runner 的注册、服务化、代理、标签、Windows 上的 shell 陷阱和安全边界（吸收第一版附录 A 与真实迁移经历）；大型 runner 与 ARC 的选择。
里程碑：定时链接巡检跑在 self-hosted runner 上。

### 第四部分 交付

**第 13 章 发布：版本、tag、Release 与可信发布**
语义化版本；变更日志的自动化；Release 与 tag 的关系；PyPI 可信发布；产物证明（attestation）。
里程碑：发布 v0.1 到 PyPI。

**第 14 章 部署：Pages、Environment 与回滚**
Pages 的两种发布方式；Environment 的审批、分支限制与密钥；部署失败与回滚；预览环境。
里程碑：站点经审批发布，并演练一次回滚。

**第 15 章 供应链与安全**
Dependabot 版本与安全更新；CodeQL；secret scanning 与推送保护；安全公告与私密漏洞报告。
里程碑：开启全部安全功能，处理第一条告警。

### 第五部分 智能体与扩展

**第 16 章 把任务交给 coding agent**
什么任务适合交出去；任务边界与验收标准；Agent 的权限和运行环境；费用；结果评审与返工。
里程碑：Agent 从 Issue 出发修复一批失效链接。

**第 17 章 Agentic Workflows：事件驱动的受控自动化**
gh-aw 的结构与编译；安全输出、staged 模式；触发条件与停止机制；成本与故障。
里程碑：每日分诊 workflow，先 staged 后正式启用。

**第 18 章 用 API、gh 和 GitHub App 扩展**
REST 与 GraphQL；`gh api` 的实用技巧；GitHub App 的认证链（JWT、installation token）；Webhook 验签与幂等（吸收第一版附录 B、C）。
里程碑：一个为链接报告发评论的 App。

**终章 发布 v1.0**
从需求到发布的完整链路复盘；哪些自动化值得保留，哪些该删掉。
