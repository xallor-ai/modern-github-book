# 第 4 章 出错之后：先判断现场，再选择恢复方式

下面用一个假设的协作场景串起本章问题。周五下午，resource-nav 的维护者小林遇到了三件事。

第一件发生在 15:40。他在本地改了半天 `resources.csv`，准备切分支前想“先清理一下”，顺手执行了 `git restore .`。半天的修改没了。

第二件发生在 16:30。他和同事老周共用一个功能分支 `feature/shared`。小林改写了自己的最后一次提交，然后 `git push --force-with-lease`。推送成功了，但半小时后老周问：“我刚推上去的提交去哪了？”

第三件是两天前的事，到今天才暴露。上周三合入的分类功能有问题，团队在 GitHub 上点了 Revert。周五修好之后再次合并同一个分支，CI 全绿，可上线后发现分类功能只回来了一半。

这三件事看起来都是“Git 把东西弄丢了”，但它们的性质完全不同：第一件里，一部分内容确实永远找不回来，另一部分其实还在；第二件是 `--force-with-lease` 在一种很常见的情况下失去了保护作用；第三件根本没有丢任何东西，是 revert 的语义和大多数人的直觉不一致。

本章不按命令逐个介绍，而是先建立一个判断框架：内容现在在哪里、是否已经被别人看到、你想要什么结果。然后按“离提交越来越远”的顺序，讲清每一层的恢复手段和它的边界。读完之后，你应该能解释小林的三件事各自发生了什么，并且知道下次怎样避免。

本章所有命令输出都来自配套脚本 `v2/labs/ch04/run.sh` 的真实运行。脚本在一个临时目录里建立裸仓库作为 origin，模拟多人协作，并对每个结论做断言。你的提交哈希会和书中不同，其余输出应当一致。

## 4.1 Git 很少真正删除东西

恢复之所以可能，是因为 Git 的存储方式。第 2 章讲过，Git 把内容存成不可变的对象：文件内容是 blob，目录是 tree，提交是 commit，每个对象用内容的哈希命名。分支、标签、HEAD 都只是指向某个提交的“指针”，也就是引用（ref）。

所以，大多数“丢失”其实只是“没有引用再指向它”。对象还在对象库里，只是从 `git log` 看不到了。只要知道它的哈希，就能把它找回来。

但这句话有两个重要的前提。

**前提一：内容必须进入过对象库。** 你在编辑器里改了文件、保存了、但从来没有 `git add` 或 `git commit`，这些修改只存在于磁盘上的工作区文件里，Git 从来没有为它们创建过对象。一旦被 `git restore`、`git checkout -- <file>`、`git reset --hard` 或 `git clean` 覆盖，Git 无能为力。这时只能指望编辑器的本地历史、操作系统的文件历史或备份。

**前提二：对象不会永远保留。** 没有被任何引用指向的对象，会在垃圾回收（`git gc`）时被清理。默认配置下：

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `gc.reflogExpire` | 90 天 | 仍可达的 reflog 记录保留多久 |
| `gc.reflogExpireUnreachable` | 30 天 | 指向已不可达提交的 reflog 记录保留多久 |
| `gc.pruneExpire` | 2 周 | 不可达的松散对象至少保留多久才会被清理 |

`git gc` 通常由 Git 在后台自动触发，而不是每次命令都运行。所以实际的恢复窗口往往比上表更长，但你不应该依赖这一点：发现问题后越早处理，能找回的东西越多。

把这两个前提合起来，可以得到一张“内容在哪一层”的表：

| 内容所在位置 | 是否在对象库 | 误删后能否用 Git 找回 | 主要工具 |
| --- | --- | --- | --- |
| 只在工作区，从未 add | 否 | 不能 | 编辑器历史、系统备份 |
| 曾经 add 过（哪怕后来取消了） | 是，作为 blob | 能，但没有文件名 | `git fsck --lost-found` |
| 在 stash 中，后来被 drop | 是，作为提交 | 能 | `git fsck --unreachable` |
| 在本地提交中，分支被移动或删除 | 是 | 能 | `git reflog` |
| 已推送到远程 | 是，且在远程 | 能 | 远程分支、他人克隆、GitHub 页面 |

这张表决定了本章的结构：后面每一节对应其中一层。

## 4.2 动手之前的三个问题

恢复操作本身通常只有一两条命令，真正困难的是选对命令。错误的恢复会制造第二次事故：用 `reset --hard` 去“撤销”一个已经推送的提交，会让所有协作者的历史和你分叉；用 `revert` 去处理一个泄漏的密钥，会让人误以为问题已经解决。

动手前先回答三个问题。

**问题一：内容现在在哪一层？** 工作区、暂存区、本地提交，还是已经在远程？上一节的表格就是为这个问题准备的。

**问题二：是否已经共享？** “共享”指的是别人可能已经拿到了它：推送到了别人会拉取的分支，或者出现在一个 PR 里。判断标准不是“我推送了没有”，而是“有没有人可能基于它继续工作”。只推送到你个人的、没有 PR 的分支，通常仍可视为未共享；一旦出现在 PR 里、或者推送到了公共分支，就应视为已共享。

**问题三：你要什么结果？** 常见的五种：

| 想要的结果 | 未共享时 | 已共享时 |
| --- | --- | --- |
| 丢弃未提交的修改 | `git restore` | 不涉及 |
| 暂时放到一边 | `git stash` 或 WIP 提交 | 不涉及 |
| 撤销某次提交的效果 | `git reset` 或 `git commit --amend` | `git revert` |
| 找回看不见的提交 | `git reflog` | 远程分支、他人克隆 |
| 从历史中彻底抹掉内容 | `git reset`、`git rebase -i` | 历史重写并协调所有人（见 4.10） |

还有一条比任何命令都重要的习惯：**在做任何会移动指针或覆盖文件的操作之前，先留一个备份。** 成本几乎为零：

```bash
git branch backup/before-fix          # 给当前提交留一个引用
git stash push -u -m "backup: before fix"   # 或者把工作区整个存起来
```

备份分支不会被推送，也不占多少空间。事情解决后用 `git branch -D backup/before-fix` 删除即可。

## 4.3 取证：读懂现场

在回答“内容在哪一层”之前，你需要看清现场。下面这个状态是脚本特意构造的：`resources.csv` 有一处已暂存的修改，`README.md` 有一处未暂存的修改，另外还有一个从未被跟踪的 `notes.txt`。

```text
$ git status --short --branch
## main...origin/main
 M README.md
M  resources.csv
?? notes.txt
```

短格式的每一行前面有两列状态码：左列是暂存区相对于 HEAD 的变化，右列是工作区相对于暂存区的变化。

| 状态码 | 含义 | 内容在哪一层 |
| --- | --- | --- |
| `M ` | 已暂存，工作区与暂存区一致 | 暂存区（已进入对象库） |
| ` M` | 已修改，未暂存 | 只在工作区 |
| `MM` | 暂存后又改了 | 两层都有，且不同 |
| `A ` | 新文件，已暂存 | 暂存区 |
| `??` | 未跟踪 | 只在工作区 |
| `UU`、`AA`、`DU`、`UD` 等 | 冲突未解决 | 合并进行中 |

第一行 `## main...origin/main` 说明当前分支和它的远程跟踪分支。如果本地有未推送的提交，这里会显示 `[ahead 1]`；如果远程有你还没合并的提交，会显示 `[behind 2]`。这一行直接回答了“是否已经推送”的一半问题。注意它基于你上次 `fetch` 时的信息，不是远程的实时状态。

除了 `status`，取证时常用的还有：

```bash
git log --oneline --graph --decorate --all -n 15   # 提交图和所有分支的位置
git diff                                            # 工作区相对暂存区
git diff --cached                                   # 暂存区相对 HEAD
git branch -r --contains <commit>                   # 这个提交已经在哪些远程分支上
```

最后一条是判断“是否已共享”的利器：如果输出里有 `origin/main` 或任何别人在用的分支，这个提交就已经共享了。

**还有一种现场需要特别识别：某个操作做到一半。** 合并冲突、rebase 冲突、cherry-pick 冲突之后，仓库处于中间状态。`git status` 的长格式会在开头提示，例如 “You have unmerged paths” 或 “interactive rebase in progress”。你也可以看 `.git` 目录里是否存在这些文件或目录：

| 存在的文件或目录 | 正在进行的操作 | 放弃命令 |
| --- | --- | --- |
| `MERGE_HEAD` | merge | `git merge --abort` |
| `rebase-merge/` 或 `rebase-apply/` | rebase | `git rebase --abort` |
| `CHERRY_PICK_HEAD` | cherry-pick | `git cherry-pick --abort` |
| `REVERT_HEAD` | revert | `git revert --abort` |

在中间状态下执行其他操作，Git 通常会拒绝，并给出提示。本章脚本第一次运行时就踩到了这个坑：一次合并冲突没有处理，后面的 `git switch` 直接失败了：

```text
fatal: cannot switch branch while merging
Consider "git merge --quit" or "git worktree add".
```

看到这类报错，第一反应应该是回到 `git status`，先决定把中间状态完成还是放弃，而不是换一个命令继续尝试。

## 4.4 未提交的修改：restore，以及“曾经暂存过”的后悔药

### restore 的三种用法

`git restore`（Git 2.23 引入）把原来 `git checkout` 承担的“恢复文件”职责单独拆了出来，语义更清楚。接着上一节的现场：

```text
$ git restore README.md
$ git restore --staged resources.csv
$ git status --short
 M resources.csv
?? notes.txt
```

第一条丢掉 `README.md` 在工作区的修改。第二条只把 `resources.csv` 从暂存区撤出来，工作区的修改仍在，所以状态从 `M ` 变成了 ` M`。这两步是分开的：`--staged` 永远不会碰工作区。

第三种用法是从任意提交里取出某个文件的旧版本：

```text
$ git restore --source=HEAD~1 resources.csv
$ git diff --stat
 resources.csv | 1 -
 1 file changed, 1 deletion(-)
```

这条命令只改工作区里的这一个文件，不移动 HEAD，也不影响其他文件。它适合“这个文件被我改坏了，我想要上一个版本的样子”这类场景。

### 哪些命令会无声地销毁工作区

下面这些命令会覆盖或删除工作区中未提交的内容，且不会进入任何 Git 记录：

| 命令 | 销毁什么 |
| --- | --- |
| `git restore <path>` 或 `git restore .` | 已跟踪文件的未暂存修改 |
| `git checkout -- <path>` | 同上（旧写法） |
| `git reset --hard` | 已跟踪文件的所有未提交修改（暂存和未暂存） |
| `git clean -f`（加 `-d` 包括目录，加 `-x` 包括被忽略的文件） | 未跟踪的文件 |
| `git switch -f`、`git checkout -f` | 与目标分支冲突的本地修改 |

对 `git clean`，永远先用 `-n` 看一遍：

```bash
git clean -nd    # 只列出将被删除的文件，不真正删除
```

### 曾经暂存过的内容可以找回

回到小林的第一件事。他执行 `git restore .` 之前，有没有对这些修改执行过 `git add`？答案决定了能找回多少。

`git add` 的实质是把文件当前内容写成一个 blob 对象存进对象库，再让暂存区指向它。之后即使你取消暂存、丢掉修改，这个 blob 也还在对象库里，只是没有任何东西指向它，成了“悬空”（dangling）对象。

脚本模拟了这个过程：往 `resources.csv` 里加一行 Pro Git 中文版，`git add`，然后连续执行 `git restore --staged` 和 `git restore`，这行内容从暂存区和工作区都消失了。接着：

```text
$ git fsck --lost-found
dangling blob 0445f2abe5cfe172708c39dbdeba3c59ddaf8635
dangling blob b1ee84d71087f63a7a3378f7feb46e8582ef66e0
```

找到了两个悬空 blob，而不是一个。第二个是刚才丢失的内容；第一个是 4.3 节那次暂存的 `Git Book` 版本，后来被 `--staged` 撤销、又被 restore 丢弃。**每一次 `git add` 都会给当时的文件内容留下一个快照。**

blob 只存内容，不存文件名，所以你需要按内容辨认。`--lost-found` 会把这些对象写到 `.git/lost-found/other/` 下，可以直接搜索：

```text
$ grep -l "Pro Git" .git/lost-found/other/*
.git/lost-found/other/b1ee84d71087f63a7a3378f7feb46e8582ef66e0

$ git show b1ee84d71087f63a7a3378f7feb46e8582ef66e0
title,url,category
GitHub Docs,https://docs.github.com/,GitHub
Python Docs,https://docs.python.org/3/,Python
Pro Git (zh),https://git-scm.com/book/zh/v2,Git
```

确认无误后，用 `git show <blob> > resources.csv` 写回文件即可。

所以小林的第一件事里，凡是 `git add` 过的修改都能找回，而 `add` 之后又在编辑器里继续写的部分找不回。由此可以得到一个实用习惯：**做到一个阶段就 `git add` 一次**。它不产生提交，也不污染历史，却给工作区留下了一个可恢复的快照。

## 4.5 stash：它其实是一个提交

`git stash` 常被当成“剪贴板”，但它的实现是提交，理解这一点能解释它所有的行为细节。

### 默认不带未跟踪文件

```text
$ git stash push -m "wip: mdn"
Saved working directory and index state On main: wip: mdn

$ git status --short
?? TODO.md
```

`resources.csv` 的修改被存走了，但新建的 `TODO.md` 还留在工作区。默认的 stash 只保存已跟踪文件。如果你本来打算“存完就切分支、清空现场”，这个遗留文件会跟着你到另一个分支上。要连未跟踪文件一起保存，用 `-u`（`--include-untracked`）：

```text
$ git stash push -u -m "wip: mdn + todo"
Saved working directory and index state On main: wip: mdn + todo

$ git status --short

$ git rev-list --parents -n 1 'stash@{0}'
7aa99f35... 5fc5e5bb... b2594e53... 7ce2cfeb...
```

最后一条命令显示 stash 提交本身（第一个哈希）和它的三个父提交：当时的 HEAD、一个记录暂存区状态的提交、一个记录未跟踪文件的提交。不带 `-u` 时只有前两个父提交。这就是 stash 能同时恢复暂存区和工作区的原因。

### pop 冲突时 stash 不会被删除

当 stash 的内容与当前分支冲突时，`pop` 会停在冲突状态，并保留这条 stash：

```text
$ git stash pop
Auto-merging resources.csv
CONFLICT (content): Merge conflict in resources.csv
...
The stash entry is kept in case you need it again.

$ git stash list
stash@{0}: On main: wip: stash side
```

这时正确的做法是像处理普通合并冲突一样解决冲突，确认无误后手动 `git stash drop`。不要反复执行 `pop`，也不要以为冲突意味着 stash 丢了。

### 误删的 stash 可以找回

`git stash drop` 和 `git stash clear` 删除的只是指向 stash 提交的引用。`drop` 会打印被删提交的哈希，这是最简单的找回线索：

```text
$ git stash drop
Dropped refs/stash@{0} (7aa99f35a5185c80f2956715969990d74f719f03)
```

如果当时没注意这一行，可以在对象库里找不可达的提交：

```text
$ git fsck --unreachable --no-reflogs | grep commit
unreachable commit 70ac9b837629c9837636756d677434e157bd19f6
unreachable commit b2594e53a958667e0e6083f8e26987b813907153
unreachable commit 7aa99f35a5185c80f2956715969990d74f719f03
unreachable commit 7ce2cfeb620d155de43118d69de153532b5afce8
```

`--no-reflogs` 让 fsck 不把 reflog 当作引用。stash 自身的记录就存在 reflog 里，drop 之后它已不在了，加上这个参数能确保结果完整。

列表里混着几类提交：更早那次 `wip: mdn` 的 stash（已被 pop，同样不可达），以及刚 drop 的这条 stash 和它的辅助父提交。你实际看到的数量可能和这里不同。用 `git log --oneline -1 <sha>` 看提交说明就能分辨：stash 提交的说明形如 `On main: wip: mdn + todo`，辅助提交以 `index on` 或 `untracked files on` 开头。找到后直接应用：

```bash
git stash apply 7aa99f35a5185c80f2956715969990d74f719f03
```

脚本验证了已跟踪的修改和未跟踪的 `TODO.md` 都回来了。

### stash 还是 WIP 提交

stash 适合“几分钟内就回来”的场景，比如临时切到 main 看一眼。如果要离开更久，更好的做法是在分支上做一个临时提交：

```bash
git switch -c wip/link-check
git add -A
git commit -m "WIP: link check, do not merge"
git push -u origin wip/link-check
```

理由有三个：stash 只在本地，换台电脑或磁盘出问题就没了，而 WIP 提交可以推送；stash 列表没有分支上下文，过两周你很难记得 `stash@{3}` 是什么；WIP 提交回来后可以用 `git reset --soft HEAD~1` 拆开继续工作，或者在合并前用 `rebase -i` 整理掉。

## 4.6 本地提交：reset 的三种模式，以及更安全的 --keep

### 三种模式各移动什么

`git reset <commit>` 的本质是移动当前分支的指针。三种模式的区别在于是否同时改写暂存区和工作区。脚本先做一个提交“feat: add Rust book”，然后分别用三种模式回退一步：

```text
--- reset --soft HEAD~1
HEAD -> feat: add Python docs
M  resources.csv

--- reset --mixed HEAD~1
HEAD -> feat: add Python docs
 M resources.csv

--- reset --hard HEAD~1
HEAD -> feat: add Python docs
(工作区干净)
```

| 模式 | 分支指针 | 暂存区 | 工作区 | 典型用途 |
| --- | --- | --- | --- | --- |
| `--soft` | 移动 | 不变 | 不变 | 合并最近几个提交、改写提交说明 |
| `--mixed`（默认） | 移动 | 重置 | 不变 | 重新组织要暂存的内容 |
| `--hard` | 移动 | 重置 | 重置 | 彻底丢弃提交和所有未提交修改 |

三种模式下，被回退的提交本身都还在对象库里。`--hard` 的危险不在于它丢掉了提交（提交可以从 reflog 找回），而在于它同时覆盖了工作区里所有未提交的修改，而那部分可能从未进入对象库。

### ORIG_HEAD：最近一次的后悔药

`reset`、`merge`、`rebase` 这类会大幅移动 HEAD 的命令，都会把移动前的位置记在 `ORIG_HEAD` 里。刚执行完 reset 就后悔了，可以直接回去：

```text
$ git reset --hard ORIG_HEAD
HEAD is now at 40ba9a9 feat: add Rust book
```

`ORIG_HEAD` 只记录最近一次，再做别的类似操作就会被覆盖。更久之前的位置要去 reflog 找（见 4.7）。

### 用 --keep 代替 --hard

多数时候你用 `--hard` 的真实意图是“把分支挪回去”，而不是“顺便把我手上没提交的修改也扔掉”。`git reset --keep` 正好满足前者：它会移动指针并更新那些在两个提交之间有差异的文件，但如果某个这样的文件有未提交的修改，它会拒绝执行：

```text
$ git reset --keep HEAD~1
error: Entry 'resources.csv' not uptodate. Cannot merge.
fatal: Could not reset index file to revision 'HEAD~1'.
```

`resources.csv` 在 HEAD 和 HEAD~1 之间有差异，而工作区里它还有一处本地修改，所以 `--keep` 拒绝了。提交和本地修改都完好无损。如果本地修改落在一个与这次回退无关的文件上（脚本里是 `README.md`），`--keep` 会正常执行，并保留那处修改。

建议把 `--keep` 当作“回退本地提交”的默认选择，只在明确想丢弃一切时才用 `--hard`，并且先用 `git status` 确认没有想保留的东西。

### 什么时候不能 reset

reset、`commit --amend`、`rebase` 都在重写历史：它们让分支指向一串新的提交，旧提交被抛弃。如果这些旧提交已经共享，别人的分支仍然基于它们，下次同步时就会出现分叉、重复提交，或者需要强制推送。判断方法就是 4.3 节的 `git branch -r --contains <commit>`，以及 `git status -sb` 显示的 ahead 数量：只有 ahead 计数里的那些提交，才是“只在本地”的。

## 4.7 reflog：本地的行车记录仪

reflog 记录了每个引用（包括 HEAD）在本地的每一次移动：提交、切换分支、reset、rebase、merge。它是找回“看不见的提交”的主要工具。

### 找回误删的分支

脚本在 `feature/link-check` 分支上做了一个尚未合并的提交，然后切回 main 删除这个分支。`-d` 会先检查分支是否已合并：

```text
$ git branch -d feature/link-check
error: the branch 'feature/link-check' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feature/link-check'

$ git branch -D feature/link-check
Deleted branch feature/link-check (was 51feded).
```

`-D` 删除时打印了分支最后指向的提交 `51feded`，这是第一条线索。如果错过了它，可以去 reflog 里找。但要注意，**分支自己的 reflog 会随分支一起被删除**（在默认的文件存储后端下）：

```text
$ git reflog show feature/link-check
fatal: ambiguous argument 'feature/link-check': unknown revision or path not in the working tree.
```

所以要看 HEAD 的 reflog，它记录了你在这个分支上工作时 HEAD 经过的每个位置：

```text
$ git reflog -n 4
5fc5e5b HEAD@{0}: checkout: moving from feature/link-check to main
51feded HEAD@{1}: commit: feat: add link checker skeleton
5fc5e5b HEAD@{2}: checkout: moving from main to feature/link-check
5fc5e5b HEAD@{3}: reset: moving to origin/main
```

`HEAD@{1}` 就是离开那个分支之前的最后一个提交。重新建立分支：

```bash
git branch feature/link-check 51feded
```

### 撤销一次错误的 rebase

rebase 出错是 reflog 最常见的使用场景。脚本模拟了一个真实的误操作：本想把分支的最后一个提交挪到 main 上，`--onto` 的起点却写错了，结果分支上较早的那个提交被悄悄丢掉：

```text
$ git log --oneline -3
a8a2734 docs: document link checker
51feded feat: add link checker skeleton
5fc5e5b feat: add Python docs

$ git rebase --onto main HEAD~1
Successfully rebased and updated refs/heads/feature/link-check.

$ git log --oneline -3
1f12949 docs: document link checker
5fc5e5b feat: add Python docs
c05270f chore: initial catalog
```

rebase 报告“成功”，没有任何警告，但 `51feded` 已经不在分支上了。在 reflog 里，一次 rebase 的记录很容易识别：

```text
$ git reflog -n 6
1f12949 HEAD@{0}: rebase (finish): returning to refs/heads/feature/link-check
1f12949 HEAD@{1}: rebase (pick): docs: document link checker
5fc5e5b HEAD@{2}: rebase (start): checkout main
a8a2734 HEAD@{3}: commit: docs: document link checker
```

`rebase (start)` 下面的那一条，就是 rebase 开始前分支所在的位置：

```text
$ git reset --hard HEAD@{3}
HEAD is now at a8a2734 docs: document link checker
```

如果 rebase 后没有做过其他会改动 ORIG_HEAD 的操作，`git reset --hard ORIG_HEAD` 也能达到同样效果。

### reflog 的边界

- **reflog 只在本地。** 它不会被推送，也不会被克隆。你看不到同事的 reflog，同事也看不到你的。
- **reflog 会过期。** 默认 90 天（记录指向不可达提交时为 30 天），见 4.1 节。
- **reflog 只记录引用的移动。** 从未提交过的内容不在里面。

reflog 的引用语法也值得记住：`HEAD@{2}` 是 HEAD 两次移动之前的位置，`main@{yesterday}` 是 main 昨天此时的位置，`@{-1}` 是上一个检出的分支。

## 4.8 已经共享：revert，以及合并之后的陷阱

### revert 一个普通提交

已经共享的提交不能从历史中拿掉，正确做法是追加一个“反向提交”来抵消它的效果：

```text
$ git revert --no-edit HEAD
[main 578d3a4] Revert "feat: add broken link"
 1 file changed, 1 deletion(-)

$ git log --oneline -3
578d3a4 Revert "feat: add broken link"
17e375a feat: add broken link
5fc5e5b feat: add Python docs
```

`--no-edit` 直接使用默认的提交说明 `Revert "..."`。去掉它会打开编辑器，让你补充撤销的原因。在团队项目里，建议写清楚原因和后续计划，因为这条提交会永久留在历史中，供以后的人理解当时发生了什么。

在 GitHub 上，已合并的 PR 页面有一个 Revert 按钮。它会创建一个新分支，里面包含反向提交，并为它开一个新的 PR。这样撤销本身也经过评审和 CI，适合处理已经合入 main 的问题。

### revert 一个合并提交

合并提交有两个父提交，Git 需要知道“相对于哪个父提交撤销”：

```text
$ git revert --no-edit f01caae
error: commit f01caae... is a merge but no -m option was given.
fatal: revert failed

$ git revert --no-edit -m 1 f01caae
[main d93eb3f] Revert "Merge feature/categories"
 2 files changed, 3 deletions(-)
 delete mode 100644 categories.py
```

`-m 1` 表示以第一个父提交为主线，也就是合并时你所在的分支（这里是 main）。效果是撤销整个功能分支带进来的所有改动。绝大多数情况下你需要的都是 `-m 1`。

### 陷阱：再次合并同一个分支

这就是小林的第三件事。功能分支 `feature/categories` 有两个提交：新增 `categories.py`，以及在 README 里加一句说明。合并后发现问题，团队 revert 了这次合并。几天后，开发者在同一个分支上补了一个测试提交，然后再次合并：

```text
$ git merge --no-edit feature/categories
Merge made by the 'ort' strategy.
 test_categories.py | 3 +++
 1 file changed, 3 insertions(+)

$ git log --oneline --graph -6
*   01b2d78 Merge branch 'feature/categories'
|\
| * 42c8806 test: cover categories
* | d93eb3f Revert "Merge feature/categories"
* | f01caae Merge feature/categories
|\|
| * 46acc60 docs: mention categories
| * d40ee73 feat: add category list
|/

$ ls
README.md
resources.csv
test_categories.py
```

合并干净利落，没有冲突，但 `categories.py` 不在了，README 里那句说明也不在了，只有新加的测试文件进来了。这个测试一跑就会失败，因为它导入的 `categories.py` 不存在。

原因在于 revert 撤销的是**内容**，不是**历史**。从提交图上看，`d40ee73` 和 `46acc60` 已经通过第一次合并成为 main 的祖先。第二次合并时，Git 计算合并基点，发现这两个提交“早就合并过了”，只需要带进来之后的新提交 `42c8806`。至于 main 上有一个提交把它们的内容删掉了，合并算法并不关心，因为那只是 main 自己的一次普通修改。

解决办法是**撤销那次撤销**：

```text
$ git revert --no-edit d93eb3f
[main d592ee3] Reapply "Merge feature/categories"
 2 files changed, 3 insertions(+)
 create mode 100644 categories.py
```

较新版本的 Git 会把这种“撤销 revert”的提交自动命名为 `Reapply "..."`。执行后，`categories.py` 和 README 的说明都回来了。

这个陷阱还有一个变体，症状完全不同。如果后续修复提交修改的正是被 revert 删掉的文件，再次合并时会出现 modify/delete 冲突：

```text
$ git merge --no-edit feature/tags
CONFLICT (modify/delete): tags.py deleted in HEAD and modified in feature/tags.  Version feature/tags of tags.py left in tree.
Automatic merge failed; fix conflicts and then commit the result.
```

这个报错对不了解背景的人来说很费解：“我只是改了一行，为什么说文件被删了？”根源仍然是同一个：main 上那次 revert 删除了文件。正确的处理同样是先 abort 这次合并，revert 那次 revert，再合并。

**团队约定建议**：一个 PR 被 revert 之后，要重新上线时，第一步是 revert 那个 revert PR（GitHub 上同样可以用 Revert 按钮），然后再在上面提交修复。在 revert PR 的描述里写明这一点，后来的人就不会掉进去。

## 4.9 被 force push 覆盖：找回与预防

### --force-with-lease 在什么时候失效

这是小林的第二件事。脚本重现了它：Alice（小林）把 `feature/shared` 推到远程，Bob（老周）拉下来，加了一个提交并推送。Alice 不知道 Bob 推送过，在本地改写了自己的提交说明，然后尝试强制推送。

`--force-with-lease` 的含义是：“只有当远程分支仍然停在我上次看到的位置时，才允许覆盖。”Alice 上次看到的位置是她自己推送的提交，而远程已经被 Bob 推进了一步，所以推送被拒绝：

```text
$ git push --force-with-lease
 ! [rejected]        feature/shared -> feature/shared (stale info)
error: failed to push some refs to '/tmp/resnav-ch04/origin.git'
```

到这里一切正常。问题在于“上次看到的位置”指的是本地的远程跟踪分支 `origin/feature/shared`，而它会被任何一次 `git fetch` 更新，包括 IDE 在后台自动执行的 fetch。Alice 的编辑器在后台 fetch 了一次，她自己并没有看 Bob 的提交，再推送时：

```text
$ git fetch
$ git push --force-with-lease
 + 36bc6fc...c66df2f feature/shared -> feature/shared (forced update)

$ git -C /tmp/resnav-ch04/origin.git log --oneline -1 feature/shared
c66df2f feat: shared v1 (reworded)
```

推送成功，Bob 的提交从远程分支上消失了。`--force-with-lease` 检查的是“远程是否还停在 `origin/feature/shared`”，而 fetch 刚把 `origin/feature/shared` 更新成了 Bob 的提交，检查自然通过。

### --force-if-includes 补上这个缺口

Git 2.30 引入的 `--force-if-includes` 增加了第二道检查：远程跟踪分支的位置必须已经出现在本地分支的历史（reflog）中。换句话说，你不只是“看到过”远程的新提交，还必须真正把它整合进自己的分支过。

脚本把远程恢复到 Bob 的提交，让 Alice 再 fetch 一次（远程跟踪分支是最新的），然后在没有整合 Bob 提交的情况下改写并推送：

```text
$ git push --force-with-lease --force-if-includes
 ! [rejected]        feature/shared -> feature/shared (remote ref updated since checkout)
hint: Updates were rejected because the tip of the remote-tracking branch has
hint: been updated since the last checkout. If you want to integrate the
hint: remote changes, use 'git pull' before pushing again.
```

这次被拒绝了，即使远程跟踪分支是最新的。建议把它设为默认：

```bash
git config --global push.useForceIfIncludes true
```

设置后，每次使用 `--force-with-lease` 都会自动带上这项检查。注意它只对 `--force-with-lease` 生效，裸的 `--force` 仍然没有任何保护，所以团队里应约定永远不用 `--force`。

### 被覆盖之后怎么找回

被覆盖的提交至少还存在于以下地方之一：

1. **推送它的人的本地仓库。** 这是最可靠的来源。Bob 的本地分支仍然指向他的提交，只要把它推到一个新分支上，就能和 Alice 的版本放在一起比较、合并：

   ```text
   $ git push origin 36bc6fc:refs/heads/feature/shared-bob
    * [new branch]      36bc6fc... -> feature/shared-bob
   ```

2. **其他协作者的克隆。** 任何在覆盖之前 fetch 过的人，他的 `origin/feature/shared` 或 reflog 里都有这个提交。
3. **GitHub 页面。** 如果分支有 PR，PR 的时间线上会出现一条 “force-pushed the branch from X to Y” 的记录，带有比较链接，X 就是被覆盖前的提交。仓库的 Activity 页面（仓库地址后加 `/activity`）也会列出 force push 及前后的提交。被覆盖的提交在一段时间内通常还能按哈希访问，但这不是 GitHub 承诺保留的东西，应尽快把它推到一个分支上。

### 从根本上预防

对 main 和发布分支，用 Ruleset 开启 “Block force pushes” 和 “Restrict deletions”（第 7 章详细讲）。对多人共用的功能分支，团队约定：改写历史前先在群里说一声；或者干脆不在共用分支上改写历史，改用追加提交，合并时再用 squash 整理。

## 4.10 推送了密钥：revert 不是答案

假设有人把含有令牌的 `.env` 提交并推送了，随后发现，执行了 revert：

```text
$ git log --oneline -S ghp_FAKE
0532bdc Revert "chore: local config"
fe62262 chore: local config
```

`-S` 搜索的是“改动中增加或删除了这个字符串的提交”。两条结果说明：令牌被加进来过，又被删掉了，而 `fe62262` 里它仍然完整地存在。任何能访问仓库的人，用这一条命令就能找到它。revert 让文件看起来干净了，但对泄漏没有任何补救作用。

正确的处理顺序是：

1. **立即吊销并轮换密钥。** 这一步优先于其他所有步骤，最好在几分钟内完成。公开仓库里的密钥会被自动化程序在很短时间内扫描到。对于部分令牌类型，GitHub 的 secret scanning 会通知令牌提供方，GitHub 自己的令牌也可能被自动吊销，但这只是补救手段，不能代替你主动吊销。
2. **评估暴露范围。** 仓库是否公开、泄漏了多久、这个密钥能访问什么、访问日志里有没有异常调用。
3. **决定是否从历史中清除。** 密钥一旦吊销，历史里留着的就只是一个失效字符串。如果仍要清除（例如合规要求，或者泄漏的是无法轮换的数据），需要用 `git filter-repo` 重写所有包含它的提交，强制推送所有受影响的分支和标签，通知所有协作者重新克隆，并联系 GitHub Support 清理缓存视图和 PR 引用中残留的提交。即便如此，已经存在的 fork 和他人的克隆你无法清理。所以第 1 步永远是关键。
4. **预防下一次。** 开启 secret scanning 的推送保护（push protection），让含有已知格式密钥的推送在到达 GitHub 之前就被拦截（第 15 章详细讲）；把 `.env` 一类文件写进 `.gitignore`；在提交前用 pre-commit 钩子做本地扫描。

## 4.11 GitHub 侧的安全网

除了本地 Git，GitHub 本身也提供了几个恢复入口。它们不能代替前面讲的方法，但在本地仓库已经不在、或者需要留下评审记录时很有用。

| 场景 | GitHub 上的入口 | 说明 |
| --- | --- | --- |
| PR 合并后删除了分支，又需要它 | PR 页面的 Restore branch 按钮 | 恢复到 PR 最后的提交 |
| 已合并的 PR 有问题 | PR 页面的 Revert 按钮 | 生成一个 revert PR，经评审和 CI 后合入 |
| 想知道谁在什么时候 force push 或删了分支 | 仓库的 Activity 页面 | 可按分支、用户、操作类型筛选，能看到前后提交 |
| PR 分支被强制推送覆盖 | PR 时间线上的 force-pushed 记录 | 带有新旧提交的比较链接 |
| 误删了整个仓库 | 账号或组织设置中的 Deleted repositories | 通常 90 天内可自助恢复，部分情况（如属于 fork 网络）除外 |

预防层面，Ruleset 能禁止对受保护分支 force push 和删除，这是唯一能从服务端阻止 4.9 节那类事故的手段。

## 4.12 团队约定清单

把本章内容落实成团队规则，可以直接写进 resource-nav 的 CONTRIBUTING：

- main 和发布分支用 Ruleset 禁止 force push 和删除。
- 已合入 main 的问题，用 GitHub 的 Revert 按钮生成 revert PR，并在描述中写明原因。
- 被 revert 的功能要重新上线时，先 revert 那个 revert PR，再提交修复。
- 共用分支上不改写历史；确需改写时，使用 `--force-with-lease`，并在全局开启 `push.useForceIfIncludes`，永远不用裸 `--force`。
- 做任何会移动指针的恢复操作前，先建备份分支。
- 推送密钥后的第一步是吊销密钥，不是改代码。

## 小结

回到开头的三件事。

**小林的第一件事**：`git restore .` 销毁的是工作区内容。曾经 `git add` 过的版本仍以悬空 blob 的形式存在，可以用 `git fsck --lost-found` 按内容找回；`add` 之后在编辑器里新写的部分，Git 从未见过，找不回来。养成阶段性 `git add` 的习惯，就是在给工作区拍快照。

**小林的第二件事**：IDE 后台的 fetch 更新了远程跟踪分支，使 `--force-with-lease` 的检查形同虚设。老周的提交仍在他自己的仓库里，推到一个新分支即可找回。开启 `push.useForceIfIncludes` 能挡住这类覆盖，Ruleset 能在服务端彻底禁止它。

**小林的第三件事**：revert 撤销内容而不撤销历史，再次合并同一个分支时，Git 认为旧提交早已合并，只带进新提交。解决办法是 revert 那次 revert。

更一般的结论是：恢复之前先回答三个问题，内容在哪一层、是否已共享、想要什么结果。Git 很少真正删除东西，但它只能保管曾经交给它的内容，而且只保管一段时间。

## 练习

1. 在一个临时仓库里，修改一个文件并 `git add`，再继续修改同一个文件但不 add，然后执行 `git reset --hard`。用 `git fsck --lost-found` 找回能找回的部分，并说明哪部分找不回、为什么。
2. 建一个功能分支，做三个提交，然后用 `git rebase -i` 删掉中间那个。只用 `git reflog` 把分支恢复到 rebase 之前的状态，并用 `git log` 验证三个提交都在。
3. 按 4.8 节的步骤重现“revert 合并后再合并”的陷阱，然后用 revert 那次 revert 的方式修复。思考：如果团队一开始用的是 squash 合并而不是普通合并，这个陷阱还会出现吗？为什么？
